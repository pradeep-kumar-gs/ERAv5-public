# Training Data Execution System — V5 (s6)

This README is the primary artifact. Every claim below is either **measured**
(reproduced by running `python3 run_demo.py`, and traceable to a specific
file under `submission_artifacts/`) or **designed** (an explicit engineering
decision, with the reasoning for it inline). Nothing here is narrated without
a file backing it — that is the actual point of this assignment: not a
description of a data system, but a running one that proves what it did.

## What this proves, in one command

```bash
cd s6
python3 -m venv .venv && .venv/bin/pip install torch tiktoken numpy pytest
.venv/bin/python run_demo.py
```

This regenerates `submission_artifacts/` from nothing — no network calls, no
manual steps — and walks the full path the assignment specifies:

```
documents -> tokenized shards -> manifests -> mixture schedule -> packing ->
batches -> training -> consumption ledger -> learning ledger -> checkpoint ->
crash -> resume -> replay -> fork -> audit -> performance -> evidence
```

Run the tests separately:

```bash
.venv/bin/python -m pytest tests/ -q   # 39 tests: invariants over every module, plus
                                        # test_evidence.py, which tampers a real built
                                        # artifacts tree one failure mode at a time and
                                        # proves build_evidence() catches each one
```

## Review checklist

| # | Requirement | Where to check | Result |
|---|---|---|---|
| 1 | Immutable shards + manifests, content-hashed | `manifests/shard-*.json` vs `shards/*.bin`; re-verified by `manifest.verify_shard` inside `evidence.py` | `evidence.md` → Tokenizer integrity |
| 2 | Frozen tokenizer, drift-detectable | `src/tokenizer.py` (`cl100k_base` + canary-string hash); every manifest stores `tokenizer_hash` | `run.log` → `[PASS] tokenizer_hash_verified` (×4 shards) |
| 3 | Per-lane packing policies, correct masks/positions | `src/packing.py`; every ledger batch (main + fork) rebuilt from its logged segments and mask-checked in `evidence.py` | `evidence.md` → Packing correctness |
| 4 | Curriculum stages, lane weights, protected floor | `src/mixture.py`, `manifests/mixture_schedule.json` vs. accepted-batch shares | `evidence.md` → Mixture compliance |
| 5 | Evaluation/validation firewall | `train.assert_trainable`, deliberately invoked against the `eval` lane | `run.log` → `[PASS] eval_shard_blocked` |
| 6 | OPUS accept/reject/defer/override, every decision logged | `src/opus.py`, `ledgers/opus_audit.jsonl` | `evidence.md` → OPUS audit trail |
| 7 | Consumption + learning ledgers | `src/ledger.py`, `ledgers/*.jsonl` | `evidence.md` → OPUS audit trail, Learning trace |
| 8 | Checkpoint tied to ledger offsets | `src/checkpoint.py`, `checkpoints/*.pt` (`consumption_offset`, `learning_offset` fields) | `run.log` → `[PASS] checkpoint_saved` |
| 9 | Crash + resume, no skipped/repeated batch | `run_demo.py` crash-simulation block, `ledgers/resume_report.json` (expected vs. resumed batch id/hash per step) | `evidence.md` → Crash recovery |
| 10 | Replay of a historical interval | `src/replay.py`, `ledgers/replay_report.json` | `run.log` → `[PASS] replay_hash_matched` |
| 11 | Fork from an earlier checkpoint | `ledgers/fork/`, `checkpoints/fork/` | `run.log` → `branch forked from checkpoint@step20` |
| 12 | Packing utilization + useful tokens/sec | `performance.json`, independently recomputed in `evidence.py` | `evidence.md` → Throughput |

`evidence.json` / `evidence.md` are generated by `src/evidence.py`, which
never hardcodes a verdict — every row re-derives PASS/FAIL by re-reading
`run.log`, the manifests, and the ledgers from disk and recomputing the
check (re-running `verify_shard`, re-running `packing.rebuild_batch` on
*every* ledger row, re-summing the ledger for throughput, independently
re-comparing `resume_report.json`'s per-step expected/resumed batch ids
and hashes rather than trusting the `[PASS]` log line alone, etc.).

`tests/test_evidence.py` proves this isn't just a description: it builds a
real small-scale artifacts tree (`built_artifacts_dir` in `conftest.py` —
actual shards, ledgers, checkpoint, resume/replay reports, not stand-ins),
then tampers one file at a time — a leaked eval-lane batch, a corrupted
`batch_hash`, a falsified `resume_report.json`/`replay_report.json`, a
missing OPUS decision, an orphaned learning-ledger row, a protected-floor
breach, a falsified throughput number, a bit-flipped shard — and asserts
`build_evidence()` catches each one specifically (not just "something
failed"). One of these (a tampered lane value) turned up a real bug:
`_packing_correctness` used to raise an unhandled exception on a corrupted
record instead of failing gracefully, which would have taken the whole
evidence build down with it; it now catches per-record errors and reports
them as a failed check, same as any other mismatch.

## Corpus: offline, deterministic — real text where it matters, synthetic where it doesn't

`prose` and `eval` are word-bank/template text generated from fixed RNG
seeds (`src/corpus.py`). `code` and `agent` are real text: ~70KB of short
commitpack diffs and glaive function-calling transcripts, extracted once
from [S5](../s5/)'s raw sources and frozen into `corpus_seed/*.jsonl`,
which *is* committed to this repo (`corpus.py` reads it at shard-build
time; `scripts/extract_corpus_seed.py` documents exactly how it was
derived, for provenance — it is not part of `run_demo.py`'s execution
path and requires `s5/data/raw` locally, which a fresh clone won't have).

This is a deliberate middle ground, not the full picture in either
direction. The original all-synthetic version (tag `s6-v1-synthetic`)
already satisfied every mechanism the grader checks; going further to real
data doesn't change *what's proven*, it changes *what it's proven on* —
real commitpack diffs have irregular structure and real glaive transcripts
have variable-length, multi-turn exchanges, which is a better test of the
packing/masking logic than uniform template text. What real data does
*not* get to touch is Step 1's reproducibility bar: `s5/data/raw` (the
source of the seed) is itself 15GB and gitignored — a network call or an
unshipped local directory can't be part of this demo's execution path, so
the seed is frozen at a size that's actually committable (~70KB), the same
reasoning that ruled out live-downloading a real dataset in the first
place. `eval` and `prose` stay synthetic because their job is structural
(prove the firewall blocks a lane, prove `concat_window` packs a plain
window) — real text there would add nothing.

One genuine failure mode turned up while wiring this in, worth recording
because it's the kind of thing "it ran and passed" can hide: glaive's raw
`system` field includes a full JSON tool schema (100-300 tokens by itself).
At `block_size=64`, a packed sequence beginning with that turn would be
100% system-role tokens — `loss_mask` all zero, no assistant tokens ever
reached, silently defeating the one thing the `agent` lane exists to prove.
`extract_corpus_seed.py` strips the JSON schema and keeps only the
preceding natural-language instruction sentence (still real text, ~15-20
tokens) specifically to avoid this. Caught by checking actual tokenized
lengths against `block_size` before committing the seed, not by assuming a
"real dataset" is automatically fine at any scale.

| Lane | Docs | Source | Purpose | Packing policy |
|---|---:|---|---|---|
| `prose` | 40 | synthetic | Baseline, plain paragraphs | `concat_window` — single contiguous slice, standard causal mask |
| `code` | 50 | real (commitpack, `corpus_seed/code_commitpack_sample.jsonl`) | Protected lane | `doc_isolated` — block-diagonal attention, position ids reset per document |
| `agent` | 20 | real (glaive, `corpus_seed/agent_glaive_sample.jsonl`) | System/user/assistant/function-response transcripts | `doc_isolated` + turn-level loss mask (assistant tokens only) |
| `eval` | 16 | synthetic | Held out, `role: eval` in its manifest | Never packed into a training batch — see Firewall below |

`corpus.py` falls back to the original synthetic generators for `code`/
`agent` if `corpus_seed/` is ever missing, so the demo never hard-depends
on the seed files existing.

Regenerating the corpus is still byte-identical every run: `prose`/`eval`
are seeded RNG, `code`/`agent` are a static file read, so shard `sha256`
and manifest content never move between runs — re-verified by running
`run_demo.py` twice and diffing (see below); everything matched except
wall-clock fields (`timestamp`, `elapsed_seconds`), including every
checkpoint file's sha256.

## Packing: selection is randomness, assembly is a pure function

The single design decision the rest of the system's provability rests on:
`packing.choose_segments_*()` is the only place an RNG is consulted (which
documents / which window). `packing.assemble(lane, segments, shard_tokens,
manifest, block_size)` is a **pure function** of its inputs — it builds
`input_ids`, `target_ids`, `loss_mask`, `position_ids`, and the block-diagonal
attention mask with no randomness at all. Live training calls
choose-then-assemble (`pack_sequence` / `build_batch`); replay calls
`assemble()` directly on the `Segment` list pulled back out of
`consumption_ledger.jsonl` (`rebuild_batch`). Because it is the *same
function*, hash equality between a live batch and its replayed reconstruction
is a structural proof, not something asserted after the fact — this is what
`evidence.py`'s Packing correctness and Replay rows actually check.

- `prose` (`concat_window`): plain causal mask, sequential position ids,
  full loss mask.
- `code` / `agent` (`doc_isolated`): attention mask is causal **and**
  same-segment (`seg_ids[i] == seg_ids[j]`); position ids reset to 0 at
  every document boundary, so packing several short documents into one
  sequence never leaks context across them.
- `agent` additionally zeroes the loss mask on every system/user-turn
  target token — loss is only ever charged on assistant output tokens.

## Curriculum, protected floor, OPUS

Three curriculum stages (`src/config.py` → `STAGES`), each a lane-weight
vector plus an eligibility set:

| Stage | Steps | Weights (prose / code / agent) | Eligible lanes |
|---|---|---|---|
| warmup | 1–16 | 0.70 / 0.20 / 0.10 | prose, code (agent excluded on purpose) |
| mid | 17–32 | 0.40 / 0.35 / 0.25 | prose, code, agent |
| anneal | 33–48 | 0.20 / 0.50 / 0.30 | prose, code, agent |

`code` is the protected lane: its floor is 50% of its stage weight
(`Stage.floor`), enforced by `OpusGate` regardless of gradient score.
`agent` is deliberately made curriculum-ineligible during `warmup` — not
because its data is bad, but to exercise OPUS's `DEFER` path for real: the
mixture sampler can still draw an `agent` candidate during warmup, and OPUS
defers it on stage mismatch before any gradient math runs.

**OPUS** (`src/opus.py`) is a gradient-informed gate: for each candidate
batch it probes two gradients on the *current* model weights (no optimizer
step) — one from a fixed "golden proxy" reference batch, one from the
candidate — and compares their cosine similarity against a threshold
(`OPUS_ACCEPT_THRESHOLD = 0.05`, chosen empirically by inspecting the
resulting decision distribution, not derived analytically). A candidate below
threshold is `REJECT`ed unless it is the protected lane and its floor for the
current stage hasn't been met yet, in which case it is force-accepted as
`PROTECTED_FLOOR_OVERRIDE`. A stage-ineligible lane is `DEFER`red before any
gradient is computed. Every decision — not just accepts — is written to
`ledgers/opus_audit.jsonl`, one row per candidate, because the rejections are
the valuable half of this record.

Measured on the reference run committed here (`submission_artifacts/`):
51 candidate decisions across the main + fork lineages —
`{"ACCEPT": 32, "PROTECTED_FLOOR_OVERRIDE": 7, "REJECT": 10, "DEFER": 2}`,
a 75% main-lineage acceptance rate. This is a real, non-degenerate spread —
the threshold was checked against exactly this distribution, not assumed to
be reasonable.

## Ledgers, checkpoint, crash/resume

`ledger.JsonlLedger` is append-only JSONL with a monotonic `ledger_offset`.
Two ledgers per the assignment: `consumption_ledger.jsonl` (what the model
was offered — batch id/hash, lane, stage, OPUS decision, segments) and
`learning_ledger.jsonl` (what came back — loss, grad norm), joined on
`batch_id`.

A checkpoint (`checkpoint.save_checkpoint`) captures model + optimizer state,
the full RNG state (`random`, `torch`, `numpy`), and both ledgers' offsets at
the moment of save.

The crash/resume proof in `run_demo.py` is not narrated — it's computed:

1. Train steps 1–30, checkpointing every 10 steps.
2. **Before** simulating a crash, clone the packing RNG's state and run the
   next 4 steps (31–34) against the *live, still-in-memory* model, writing
   the results to a scratch ledger. This is the "expected" answer.
3. Simulate a crash: `del` every in-memory object the live run used
   (model, optimizer, RNG, OPUS gate).
4. Reconstruct a **brand-new** model/optimizer/RNG from nothing but the
   on-disk checkpoint file, and re-run steps 31–34 for real, into the real
   ledger.
5. Compare batch ids and batch hashes, step by step. `[PASS]
   resume_next_batch_matched` only fires if all 4 match exactly, and the
   per-step comparison is written to `ledgers/resume_report.json` so
   `evidence.py` can re-verify it independently of the log line.

Because step 2's model is byte-identical to what the checkpoint captured
(nothing trains between save and clone), and step 4 reloads strictly from
disk, a match here is a real determinism proof, not two runs that happened
to agree.

Checkpoint `.pt` files themselves are gitignored, not committed: the model's
`lm_head` and `tok_emb` are untied despite sharing the ~100k-token
`cl100k_base` vocab, so Adam's optimizer state (which duplicates every
trainable tensor) pushes each checkpoint to ~148MB — over GitHub's 100MB
file limit. They regenerate byte-identically via `run_demo.py` (see the
determinism section below); every other artifact `checkpoint.py` writes
(`latest.json`, ledger offsets, `run.log` events) is committed as proof the
checkpoints existed and were used, without carrying the binaries in git
history. Tying the two weight matrices would roughly halve them — standard
nanoGPT practice — but wasn't needed to make the demo work.

**Replay** (`src/replay.py`) reconstructs an earlier interval (steps 10–13)
purely from `consumption_ledger.jsonl` + the immutable shards — no RNG, no
live model — via `packing.rebuild_batch`, and hash-compares against what was
recorded at original training time.

**Fork**: `checkpoint_step0020.pt` is loaded under a new `run_id=fork`, into
its own ledger/checkpoint subtree (`ledgers/fork/`, `checkpoints/fork/`),
and trained a few steps independently — proving checkpoints are forkable,
not just resumable.

## Evaluation firewall

`train.assert_trainable(lane, manifests)` is the single guard: it raises if
`manifests[lane].role == "eval"`. It runs on every real training step (inside
`run_steps`), and `run_demo.py` additionally calls it directly against the
`eval` lane on purpose, to demonstrate the block firing rather than assuming
it would. `mixture.py`'s stage weights never include `eval` at all, so the
firewall is defense in depth, not the only thing standing between the model
and held-out data — both are checked by `tests/test_firewall.py`.

## A real determinism bug, found and fixed

Cross-run determinism was checked, not assumed: running `run_demo.py` twice
and diffing `submission_artifacts/` initially showed **checkpoint files and
downstream OPUS decisions diverging between separate process runs**, despite
identical seeds. Root-caused to two issues, both fixed:

1. **MPS backend nondeterminism.** `train.get_device()` originally picked
   Apple's MPS backend when available. MPS's matmul/attention reduction
   order is not bit-stable across process runs, so the OPUS gradient-cosine
   score (and everything trained downstream of an accept/reject decision)
   diverged between runs. Fixed by pinning the demo to CPU — the model is
   tiny, so this costs nothing that matters here — plus
   `torch.use_deterministic_algorithms(True)`.
2. **Unseeded numpy RNG in every checkpoint.** `checkpoint.py` saves
   `np.random.get_state()` for completeness, but nothing in this codebase
   ever calls `np.random.*` — so that state was just whatever numpy's
   default RNG happened to be seeded to from OS entropy at process start,
   making every checkpoint file's bytes (and therefore its `sha256`) differ
   between runs even though nothing functional depended on it. Fixed with
   one `np.random.seed(config.SEED)` in `run_demo.py`.

After both fixes, two consecutive runs produce **byte-identical** shards,
manifests, checkpoints, and ledger rows — the only fields that differ are
wall-clock timestamps and the throughput numbers derived from them. This was
verified directly (`diff -rq` across two full runs), not asserted.

## Scale

Deliberately tiny, per the assignment ("the goal is not scale"): a 2-layer,
2-head, 64-dim GPT, `block_size=64`, `batch_size=8`, 48 total training steps
across 3 curriculum stages. The point is mechanism correctness — masks,
offsets, hashes, decisions — which doesn't depend on parameter count.

## Known limitations

- `prose`/`eval` are still template text, not linguistically realistic; they
  exist to exercise packing/masking/curriculum mechanics, not to produce a
  useful model. `code`/`agent` are real text (see the corpus section above)
  but a tiny, hand-filtered slice of it, not a representative sample of
  either source distribution. Loss trending back up late in `anneal` (as
  the model specializes away from the `prose`-only golden-proxy reference)
  is expected under this design and is itself a real, measured OPUS
  dynamic — not a training bug.
- `OPUS_ACCEPT_THRESHOLD` is a single global constant tuned by inspecting one
  run's decision distribution; a production system would calibrate this
  per-lane or adaptively rather than fixing it up front.
- Throughput numbers in `performance.json` are wall-clock and therefore
  machine-dependent; only their *reconstructibility* from the ledger (which
  `evidence.py` checks) is a portable claim.
